# Camera Support

Tested camera sensors, overlay names as they appear to jetson-io, verification commands, and known issues. To build, install, or write a camera device-tree overlay, see [camera_overlays.md](camera_overlays.md).

## Tested Cameras

| Sensor | Lanes | Resolution | Overlays | Status |
|--------|-------|------------|----------|--------|
| IMX219 | 2     | 3280x2464  | dual (JAJ/PAB_V3), quad (PAB) | Working |
| IMX477 | 2     | 4056x3040  | dual (JAJ/PAB_V3), quad (PAB) | Working |
| IMX708 | 2     | 4608x2592  | dual (JAJ/PAB_V3), quad (PAB) | Working |
| OV64B40 (FLIR Hadron EO) | 4 or 2 | 9248x6936 | one per CSI port | Working (V4L2) |

Each carrier ships exactly one overlay per sensor: dual on JAJ / PAB_V3 (two CSI ports), quad on PAB (four CSI ports). The FLIR Hadron EO is the exception: it is one camera, so it ships one overlay per port. The image already includes every overlay for that product; switch with `jetson-io` (details in [camera_overlays.md](camera_overlays.md)). Each carrier also bakes an IMX219 overlay at flash time so cameras work on first boot without a jetson-io step (quad on PAB, dual on JAJ and PAB_V3).

The quad overlay is new and not yet hardware-validated: it pairs the port wiring of the IMX219 quad (the PAB default) with the sensor modes of the retired single overlay.

### 4-Lane Mode (Not Working)

IMX477 4-lane overlays have been removed. While the Sony IMX477 sensor silicon supports 4 lanes, the RidgeRun `nv_imx477` driver's 4-lane register initialization tables are incorrect. Getting correct values requires access to the Sony sensor NDA documentation. NVIDIA has acknowledged their own `imx477-dual-4lane.dts` reference overlay is broken.

2-lane mode provides full 12MP at 30fps which is sufficient for most use cases.

## FLIR Hadron EO (OmniVision OV64B40, 64MP)

The visible camera of the FLIR Hadron 640R / 640R+, connected through the ARK Hadron Adapter. The Hadron's Boson thermal camera is separate: it enumerates over USB as a UVC device (`09cb:4007`) and needs no overlay.

Driver is `nv_ov64b40`, vendored under `kernel_overlay/`. Its register tables are generated by `scripts/camera/mtk_to_reg8.py` from the OV64B imgsensor driver in realme's GPL-2.0 Narzo 50 / 8i kernel release (24 MHz input, D-PHY 4-lane). The Hadron's own oscillator is 24 MHz: every mode runs at its designed rate. On a 2-lane port the driver sets the sensor's MIPI lane count to two (`0x3012` = `0x21`, as the same-generation ov08x40 driver does) and doubles each mode's line length (HTS). Every mode then keeps its lane rate and runs at half the frame rate.

**Status:** V4L2 RAW10 capture works on JAJ CAM1 (4-lane) and CAM0 (2-lane), in all four modes, with exposure and gain controls. It has been bench-tested on JAJ only. Argus (`nvarguscamerasrc`) does not work yet: there is no ISP tuning for this sensor, and the flash-time IMX219 `module1` stays in the camera platform under the Hadron overlay.

| 0 | 4624x3468 | 30 | 15 | 1699.2 Mbps | 4-cell binned (default) |
| 1 | 3840x2160 | 60 | 30 | 2300 Mbps | |
| 2 | 2304x1296 | 120 | 60 | 1699.2 Mbps | |
| 3 | 9248x6936 | 13.2 | 6.6 | 2400 Mbps | Full array, on-sensor remosaic |

### Capture

The Hadron EO is a `vi-output, ov64b40` node; its `/dev/video*` number depends on whether the Boson's UVC nodes enumerate first.

```
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoN --set-fmt-video=width=4624,height=3468,pixelformat=BG10 \
  --set-ctrl bypass_mode=0,sensor_mode=0,exposure=8000,gain=32 \
  --stream-mmap --stream-count=30 --stream-to=hadron.raw
```

- **Pixel format:** BGGR RAW10, stored MSB-aligned in 16-bit words (`value >> 6`).
- **Exposure and gain:** exposure is in microseconds; gain is in units of 1/16, so 16 is 1x and 248 is 15.5x. Both can be set before streaming or while streaming.
- **Frame rate:** each mode starts at its own rate. Change it with `frame_rate` (fps × 10^6) while streaming.

### Live view

`scripts/camera/hadron-view/` shows the EO and the Boson side by side, fullscreen on the Jetson's display. A panel beside them plots the adapter's ICM-45686 against the frame timing. Every timestamp is on `CLOCK_MONOTONIC`, so the panel shows where IMU samples land within each EO exposure and relative to each IR frame's sync pulse.

- **Install:** copy the directory to the Jetson (`scp -r scripts/camera/hadron-view jetson@<ip>:`). The launcher expects it at `/home/jetson/hadron-view`. Then trust the launcher: `cp ~/hadron-view/hadron-view.desktop ~/Desktop/ && gio set ~/Desktop/hadron-view.desktop metadata::trusted true`. It needs `gcc` and `xdotool`.
- **Run:** use the desktop launcher, or `~/hadron-view/start.sh` over SSH. Quit with q, Esc or a right click; from SSH, run `stop.sh`. Status lines go to `view.log`. If the driver isn't loaded, `start.sh` loads it after a password prompt. A locally built `nv_ov64b40.ko` next to the scripts takes precedence over the installed module.
- **EO:** mode 2 (2304x1296) at 25 fps, so each frame spans a whole number of 200 Hz IMU samples. Without ISP tuning the viewer renders the raw Bayer itself: 2x2 binning, gray-world white balance, auto exposure and gamma.
- **Latency:** about 12 ms for the EO, from mid-exposure (about 20 ms on a 2-lane port, where the readout takes twice as long), and about 23 ms for the IR, from its sync pulse (13 ms from its UVC timestamp). Both are measured up to the display sink, before the wait for vsync; the panel shows them live.
- **IMU:** polled over `i2c-1` at 200 Hz, because INT1 is not wired.
- **Frame sync:** while the view runs, the Boson is the Hadron's sync master (see [Frame sync](#frame-sync)); quitting sets it back to disabled. The ICM-45686 tags each pulse through FSYNC, which needs R12 fitted on the adapter, and the Jetson timestamps the same pulses on the port's MCLK pad. A line fitted between the two puts the IMU samples on `CLOCK_MONOTONIC` to about 2 µs rms, where the viewer otherwise relies on host read times (about 0.3 ms late). By default the viewer timestamps the pad the overlay made the sync input; `--sync-line` names another GPIO line (CAM0 is `PP.00`), and `--no-sync` leaves the Boson alone.

### Hardware notes

Bench-verified on JAJ CAM0 and CAM1:

- **I2C:** the sensor is at 7-bit `0x36`, with a second SCCB ID at `0x21`. Its chip ID, read 24-bit from `0x300a`, is `0x566442`. `I2C_CAM` also carries the Boson CCI at `0x6a` and EEPROMs at `0x50`/`0x51`, which answer even while the sensor is held in reset.
- **Reset:** the carrier's `CAMn_PWDN` drives Hadron `/HADRON_RST` through the adapter. High releases the sensor. FLIR says this line also resets the Boson, but a 1 s low pulse did not drop the Boson off USB. The driver releases reset once and never drives it low; standby is software (`0x0100`).
- **No MCLK:** the Hadron connector has no clock pin, because the EO has its own oscillator. The adapter routes the carrier's `CAMn_MCLK` to Hadron pin 43 `EXT_VSYNC`, so the overlays declare no clocks. The bootloader leaves that pad driving as a clock output, so each overlay makes it a pulled-down input (see [Frame sync](#frame-sync)). The overlay sets this as the pinmux controller's default state, as jetson-io's 40-pin header configurations do; combined with one of those, only one of the two states applies.
- **Orientation:** with the tables' phone-module mirror and flip, the EO reads out rotated 180° relative to the Boson in the same housing. The overlays set `rotation = <180>`, and the driver undoes both while keeping BGGR.
- **Adapter I2C:** the adapter's ICM-45686 IMU (`0x68`) and the Hadron's internal IMU (`0x28`) are on the Hadron control I2C (JAJ J36, module I2C0), not on the camera bus.

### Frame sync

Hadron pin 43 `EXT_VSYNC` is one net inside the Hadron that joins the Boson's sync pin and the EO sensor's (Hadron 640R engineering datasheet, figure 7). On the ARK Hadron Adapter, R11 joins it to the carrier's `CAMn_MCLK` and R12 (not fitted by default) to the ICM-45686's FSYNC pin. Bench-verified on JAJ CAM1 and CAM0:

- **Boson:** the ext sync mode is set over its USB serial port, and it lasts until the Hadron is power-cycled. When disabled (its power-on setting), the Boson holds the line low. As master it outputs a short high pulse for each 60 Hz core frame. As slave its frames follow pulses on the line; it has followed 60 Hz pulses from the Jetson, and it stops sending frames without them.
- **EO:** the OV64B40's sync pin does not drive the line with these tables. The EO free-runs on its own oscillator and is not locked to the Boson.
- **IR frames:** this Boson has its smart averager on, so USB carries 30 fps, each frame the average of two 60 Hz core frames. Each frame's UVC timestamp, at its first USB packet, comes 9.4 to 9.6 ms after every second pulse, and it moves with that pulse when the pulse moves. How old the image already is at that pulse can't be seen from timing alone.
- **Carrier pad:** the bootloader configures `CAMn_MCLK` as a driven clock output, which would fight the Boson as master. Each overlay therefore makes the port's pad a pulled-down input: CAM0 `PP.00` and CAM1 `PP.01` on every carrier, plus PAB CAM2 `PQ.05` and CAM3 `PQ.06` (from the schematics; JAJ CAM0 and CAM1 are bench-tested). The pulses can then be timestamped on that GPIO line.
- **IMU:** with R12 fitted, the ICM-45686 tags the first sample after each pulse with the pulse-to-sample delay, at 1 µs resolution. Pin 9 then has to be switched from its power-on INT2 function to FSYNC. Over 20 s, the IMU measured the pulse spacing to 0.7 µs std; the Jetson's interrupt timestamps of the same pulses scatter by about 26 µs, with about 0.7% of them late by about 200 µs.

## Selecting an overlay (runtime)

```
sudo /opt/nvidia/jetson-io/config-by-hardware.py -l
sudo /opt/nvidia/jetson-io/config-by-hardware.py -n 2="Camera IMX477 Quad"
sudo reboot
```

Use the `overlay-name` string from the list (header number for the 22pin CSI connector is typically 2). Build, custom overlays, flash-time defaults, and troubleshooting: [camera_overlays.md](camera_overlays.md).

## Test Commands

### Verify Camera Detection

```
nvargus_nvraw --lps
```

### v4l2-ctl

Capture 300 frames from /dev/video0:
```
v4l2-ctl --set-fmt-video=width=3840,height=2160,pixelformat=RG10 --stream-mmap --stream-count=300 -d /dev/video0
```

### GStreamer

A provisioned image (the build default) already ships the Tegra GStreamer plugins (`nvarguscamerasrc`, `nvvidconv`, `nvv4l2*`) via `nvidia-l4t-gstreamer`. Install `nvidia-jetpack` only if you also need the full CUDA/TensorRT compute stack.

UDP h.264 stream (replace IP/port):
```
gst-launch-1.0 nvarguscamerasrc ! nvvidconv ! \
  x264enc key-int-max=15 bitrate=2500 tune=zerolatency speed-preset=ultrafast ! \
  video/x-h264,stream-format=byte-stream ! \
  rtph264pay config-interval=1 name=pay0 pt=96 ! \
  udpsink host=192.168.0.96 port=5600 sync=false
```

Record to file:
```
gst-launch-1.0 nvarguscamerasrc ! \
  'video/x-raw(memory:NVMM), width=3840, height=2160, format=NV12, framerate=30/1' ! \
  nvvidconv ! x264enc key-int-max=15 bitrate=2500 tune=zerolatency speed-preset=ultrafast ! \
  h264parse ! mp4mux ! filesink location=output.mp4
```

Select a specific sensor (for dual camera setups):
```
gst-launch-1.0 nvarguscamerasrc sensor-id=0 ...
gst-launch-1.0 nvarguscamerasrc sensor-id=1 ...
```

## Known Issues

**JetPack 6.2.2 / R36.5.0 Argus regression** (bench-reproduced on PAB_V3/Orin NX with dual IMX219): every `nvarguscamerasrc` teardown errors (`CANCELLED` / `Argus Correctable Error Status`), and roughly 1 in 60–120 camera relaunches fails outright — no frames, then a nvargus-daemon segfault and a ~40 s video outage. Introduced by NVIDIA in the L4T 36.4.7 userspace refresh, still present in 36.5.0; the kernel/device tree/RCE firmware are not involved, and NVIDIA's forum workaround (keeping the camera RTCPU powered) does **not** prevent it on Orin NX. Fix shipped in this repo: provisioning (the build default) pins the camera userspace stack (gstreamer/camera/multimedia debs) to the last good release via `NV_CAMERA_STACK_VERSION` in `versions.env`. Full evidence, repro protocol, and bench data: [argus_relaunch_regression.md](argus_relaunch_regression.md) (issue [#107](https://github.com/ARK-Electronics/ark_jetson_kernel/issues/107)).
